# Кабинет клиента

Состояние на 2026-09-23. Продолжение `2026-09-19-orders-and-hours-design.md` и
спеки `habibi_ui` (`habibi_ui/docs/superpowers/specs/2026-08-14-habibi-ui-design.md`):
бот уже принимает заказы, теперь владельцу бизнеса нужно место, где он их видит
и настраивает бота, не заходя в Desk.

## 1. Задача

Клиент Habibi — мелкий бизнес на 1–3 человека: бургерная, автопрокат, магазин
электроники, туры. Под каждого поднимается отдельный сайт ERPNext. Супер-админ
видит на нём всё — Desk, модули, консоль отладки ИИ. Владельцу бизнеса нужно
другое: **простой кабинет**, где есть только его разделы и только нужные поля.

В кабинете владелец:

- заполняет данные компании для бота и подключает Telegram;
- ведёт каталог (меню) и режим работы;
- видит переписки, может перехватить разговор у бота;
- видит черновики заказов от бота, принимает или отклоняет их, клиент получает
  об этом сообщение;
- видит клиентов.

Бизнесы разные, поэтому кабинет **не пишется под бургерную**. Раздел — это
запись в настройках, набор разделов под вид бизнеса — пресет вертикали. В этой
задаче делается механизм и один пресет, «общепит».

Цепочка задач, из которых эта — первая:

1. **Кабинет клиента** — этот документ.
2. **Вертикали** — пресеты «аренда», «розница», «туры» и модуль бронирования
   по датам, которого у общепита нет.
3. **Управление тенантами** — `saas_bridge` создаёт сайт и применяет пресет,
   разделы включаются из админки.

## 2. Что уже есть

| Что | Где |
|---|---|
| SPA на Vite + React, лаунчер воркспейсов, консоль отладки ИИ (`/ai`) | `habibi_ui/frontend/src` |
| Методы `habibi_ui.api.v1.*`, генерация типов | `habibi_ui/habibi_ui/api/v1`, `test_typegen.py` |
| Меню: `Item` + `Item Price` по прайс-листу из `Selling Settings`, правила действующей цены | `habibi_ai/tools/menu.py` |
| Зоны доставки: `Delivery Zone` | `habibi_core` |
| Режим работы: `Working Hours` + слоты + исключения | `habibi_ai` |
| Расчёт заказа: `AI Order Quote`, ссылка на канальный чат и `sales_order` | `habibi_ai` |
| Чат канала с паузой бота: `AI Channel Chat.ai_paused`, `paused_reason` | `habibi_ai` |
| Telegram: `Telegram Account` (личный аккаунт, MTProto), `Telegram Bot`, `Telegram Chat`, `Telegram Message`, `Telegram Message Template` (с переводами) | `habibi_telegram` |
| Воркфлоу Sales Order `Habibi Burger Order`: `New` → `Confirmed` → `In Kitchen` → `Ready` → `Out for Delivery` → `Delivered`; `Cancelled` | заведён руками на `erp.habibi-erp.com` |
| Свои поля Sales Order `custom_*` (способ получения, зона, источник, телефон) | заведены руками там же |

Промпт и конфигурация бота лежат в Directus (три коллекции) и остаются там под
супер-админом. Владелец промпт не видит и не правит.

Воркфлоу и свои поля Sales Order есть не на каждом сайте. Код проверяет их
наличие и работает без них (см. 6.1).

## 3. Роли и вход

| Роль | Видит |
|---|---|
| `Habibi Owner` | весь кабинет |
| `Habibi Staff` | главная, заказы, переписки, клиенты; настроек (меню, зоны, режим работы, профиль, Telegram) не видит |
| System Manager | как сейчас: лаунчер, Desk, `/ai`; кабинет открывается по `/c` |

Пользователь с ролью `Habibi Owner` или `Habibi Staff` после входа попадает в
кабинет (`/c`), остальные — в лаунчер, как раньше. Решение принимает сервер в
`session.me()`, фронт только перенаправляет. Desk владельцу не закрывается
специально: у него нет прав на лишние DocType, и этого достаточно.

## 4. Настройки кабинета

### 4.1 `Cabinet Settings` (single, `habibi_ui`)

Таблица `sections` (`Cabinet Section`):

| Поле | Смысл |
|---|---|
| `key` | уникальный ключ раздела, он же часть URL: `/c/<key>` |
| `label`, `icon`, `idx` | подпись, иконка, порядок в меню |
| `kind` | `generic` — рисуется из записи; `custom` — рукописный экран |
| `screen` | для `custom`: имя экрана из реестра фронта (`chats`, `hours`, `profile`, `telegram`, `home`) |
| `ref_doctype` | для `generic`: DocType |
| `list_fields` | для `generic`: поля списка, по строке на поле |
| `form_fields` | для `generic`: поля формы, по строке на поле |
| `base_filters` | для `generic`: JSON фиксированного фильтра, который владелец не снимает |
| `can_create`, `can_edit`, `can_delete` | что разрешено в кабинете (поверх прав Frappe, не вместо) |
| `roles` | кому раздел виден; пусто — всем ролям кабинета |
| `feature` | флаг возможности, без которого раздел скрыт (например, `delivery`) |

Строка поля — `fieldname` или `fieldname:Подпись`. Имя с префиксом `@` —
адаптер (4.3).

### 4.2 Сервер режет поля

Методы `habibi_ui.api.v1.cabinet`:

```
config()                          → разделы, доступные пользователю, с метой полей
list(section, filters, page)      → строки, только list_fields
get(section, name)                → документ, только form_fields
save(section, name|None, values)  → только form_fields, только при can_create/can_edit
delete(section, name)             → только при can_delete
```

Правило: **ни одно поле вне конфигурации раздела не читается и не пишется**,
даже если пользователь имеет на него право в Frappe. Лишние ключи в `values`
отбрасываются до `doc.update`. `base_filters` склеиваются с фильтрами клиента
через AND и не могут быть сняты. Запись — только через
`frappe.get_doc(...).save()`, права Frappe проверяются как обычно.

Методы кабинета работают с правами пользователя, поэтому у ролей `Habibi
Owner/Staff` должны быть права Frappe на DocType своих разделов — и через
`/api/v2` эти документы видны целиком. Это приемлемо: это данные самого
клиента на его собственном сайте. Граница безопасности — **набор DocType**, на
которые у ролей есть права (фикстура ролей в `habibi_ui`), а не набор полей.
Фильтр полей в кабинете защищает от случайной порчи служебных полей и держит
экран простым; `base_filters` и `can_*` работают так же.

Раздел, чей DocType или поле на сайте отсутствует, в `config()` не попадает;
причина пишется в лог (`frappe.logger("habibi_ui")`). Кабинет из-за одного
раздела не падает.

### 4.3 Адаптеры

Поле, которого нет в DocType, но которое нужно показать, — адаптер в коде:
пара функций `read(docs) → {name: value}` и `write(doc, value)`, регистрация в
`habibi_ui/cabinet/adapters.py`.

Первый адаптер — `@selling_price` для `Item`: действующая цена в прайс-листе из
`Selling Settings`. Чтение — по тем же правилам действующей цены, что у бота
(общая функция из `habibi_ai`, без копии). Запись — обновить или создать
`Item Price` с `valid_from` сегодня. Нет прайс-листа в настройках — поле
показывается пустым и не редактируется, с подсказкой «Не задан прайс-лист».

### 4.4 Флаги возможностей

В `Habibi AI Settings` — таблица включённых возможностей (`delivery`,
`orders`, …). Флаг управляет двумя вещами сразу: виден ли раздел кабинета и
доступен ли боту соответствующий инструмент (`get_delivery_zones`,
`quote_order`/`create_order`). Выключенная доставка — ни раздела, ни
инструмента, и бот о доставке не говорит.

### 4.5 Пресет вертикали

`habibi_ai/presets/<vertical>.json`: разделы, флаги, заголовки правил профиля
с подсказками, шаблоны сообщений. Применяется командой

```
bench --site <site> habibi-ai apply-preset food
```

Идемпотентно: существующий раздел с тем же `key` обновляется, заполненный
текст правила и отредактированный шаблон не перезаписываются, чужие разделы
не удаляются. Второй запуск подряд ничего не меняет.

## 5. Бизнес-профиль

`Business Profile` (single, `habibi_ai`) — то, что бот знает о компании.

| Поле | Смысл |
|---|---|
| `business_name`, `business_kind` | название, вид деятельности |
| `address`, `phone` | адрес, телефон для клиентов |
| `description` | коротко о бизнесе, 2–5 предложений |
| `tone` | тон общения: `friendly` / `neutral` / `formal` |
| `rules` | таблица `Business Profile Rule`: `title`, `hint`, `text` |

Режим работы в профиль не дублируется — он читается из `Working Hours`.

Профиль собирается в блок промпта на каждом ходе в `run_turn`, чистой функцией
без frappe (быстрые тесты). Правило с пустым `text` в промпт не попадает.
Порядок: ядро, затем правила в порядке таблицы.

Правила у каждого бизнеса свои. Пресет «общепит» заводит «Доставка», «Оплата»,
«Самовывоз»; у аренды это были бы «Залог», «Документы», «Возврат авто».

## 6. Экраны

Раскладка сначала под телефон: снизу таб-бар (Главная, Заказы, Переписки,
Ещё), настройки — в «Ещё». На широком экране — боковое меню.

| Раздел | Вид | Данные |
|---|---|---|
| Главная | `custom: home` | новые заказы, чаты за сегодня, чаты на паузе, лента событий |
| Заказы | `generic` + действия | `Sales Order` от бота |
| Переписки | `custom: chats` | `Telegram Chat/Message` + `AI Channel Chat` |
| Клиенты | `generic`, только чтение | `Customer` |
| Меню | `generic` | `Item` + `@selling_price` |
| Зоны доставки | `generic`, флаг `delivery` | `Delivery Zone` |
| Режим работы | `custom: hours` | `Working Hours` |
| О компании | `custom: profile` | `Business Profile` |
| Telegram | `custom: telegram` | `Telegram Account` |

Главная и пустые разделы, когда Telegram не подключён, показывают плашку
«Подключите Telegram» со ссылкой на мастер.

### 6.1 Заказы

Список: номер, клиент, телефон, сумма, способ получения, время, статус.
`base_filters` пресета — заказы, у которых есть `AI Order Quote`. Статус —
`workflow_state`, если воркфлоу есть, иначе docstatus словами.

Карточка: состав, адрес и зона, комментарий, ссылка «Открыть переписку»,
кнопки действий.

Действия — метод `habibi_ui.api.v1.orders.transition(name, action)`:

- **Есть воркфлоу** — кнопками показываются переходы, доступные пользователю из
  текущего состояния (`frappe.model.workflow.get_transitions`), выполняются
  через `apply_workflow`. «Принять» — переход из `New`, ведущий к проведению;
  «Отклонить» — переход в `Cancelled`.
- **Воркфлоу нет** — «Принять» = `submit`, «Отклонить» = `cancel` проведённого
  или удаление черновика.

Какой переход считается «принять», а какой «отклонить», задаёт пресет (имена
действий воркфлоу); без пресета — по умолчанию выше.

### 6.2 Уведомление клиента

После «Принять» и «Отклонить» кабинет показывает текст сообщения по шаблону;
владелец может его поправить и отправить или пропустить.

1. Сначала переход заказа. Не прошёл — ошибка сервера на экран, сообщение
   не отправляется, заказ как был.
2. Затем отправка в канальный чат из `AI Order Quote` через
   `Telegram Chat.send_message` — от имени бота.
3. Результат отправки пишется в заказ (комментарий в таймлайне: отправлено /
   ошибка и текст). Отправка сорвалась — заказ остаётся принятым, в карточке
   «Клиент не уведомлён» и кнопка «Повторить».

Шаблоны — `Telegram Message Template` `order_accepted` и `order_rejected` из
пресета. Подстановки: `{order}`, `{customer}`, `{total}`, `{reason}`,
`{time}`. У заказа без канального чата (создан вручную) шаг уведомления не
показывается.

### 6.3 Переписки

Слева список чатов: имя клиента, превью, время, метка «бот на паузе». Справа
лента: клиент, бот и сотрудник различаются. Сверху — карточка клиента и его
заказы.

- **«Взять на себя»** — `ai_paused = 1`, `paused_reason = operator`; появляется
  поле ответа, сообщение уходит в Telegram от имени бота.
- **«Вернуть боту»** — пауза снимается.

Методы — `habibi_ui.api.v1.chats.{list, messages, send, pause, resume}`. Экран
не знает про Telegram напрямую: канал — адаптер на сервере, WhatsApp позже
ложится рядом.

### 6.4 Режим работы, профиль, Telegram

- **Режим работы** — неделя строками (день → с/до или «выходной», несколько
  интервалов в день), ниже исключения на даты. Сохраняет `Working Hours`
  целиком одним вызовом.
- **О компании** — поля ядра и блоки правил; у пустого блока видна подсказка
  из пресета. Владелец может добавить свой блок.
- **Telegram** — вход в настоящий Telegram-аккаунт бизнеса (`Telegram Account`,
  MTProto из `habibi_telegram`): клиенты пишут именно в него, и ИИ отвечает
  от его имени. Шаги: телефон → код из Telegram → пароль двухэтапной
  проверки (только если он включён на аккаунте). `api_id`/`api_hash` — одни
  на платформу, лежат в `common_site_config` (`telegram_api_id`,
  `telegram_api_hash`); владелец их не видит, а без них экран отвечает
  «Подключение Telegram не настроено на сервере». Методы —
  `habibi_ai.cabinet.settings.telegram_status / request_code / sign_in /
  disconnect`; состояние экрана: `none`, `code_sent`, `password_needed`,
  `connected`, `error` (сессию отозвали из Telegram). Аккаунт кабинета —
  единственный на сайте; если их несколько — тот, где включён ИИ, иначе
  самый ранний. Уже вошедший аккаунт (заведённый руками) сразу виден
  подключённым. После входа включаются приём сообщений (`enabled`,
  `sync_enabled` — их забирает cron/слушатель `habibi_telegram`) и ИИ
  (`ai_enabled`, без ответов в группах); бот ИИ ставится, только если у
  тенанта он один, иначе экран показывает «ИИ-бот не выбран — обратитесь к
  администратору». Подключённый аккаунт: «Подключён: имя (@username),
  телефон, последнее сообщение N минут назад» и «Отключить» с
  подтверждением. Код и пароль нигде не сохраняются; ошибки Telegram —
  русским текстом, исходное сообщение только в лог.
  `Telegram Bot` в кабинете нет: это бот уведомлений сотрудникам.

## 7. Живое обновление

Сервер публикует realtime-события (`frappe.publish_realtime`, комната сайта)
при вставке `Telegram Message`, при вставке и смене состояния `Sales Order`
с расчётом, при смене паузы `AI Channel Chat`. Фронт по событию инвалидирует
нужные запросы TanStack Query. Полинга нет.

## 8. Тесты

Быстрые, без frappe:

- фильтр полей раздела: лишнее поле не читается и не пишется, адаптер
  распознаётся, `base_filters` не снимается;
- сборка профиля в блок промпта;
- слияние пресета: заполненное не перезаписывается, повтор — без изменений;
- подстановка шаблона уведомления.

На сайте:

- `cabinet.config/list/get/save/delete` под `Habibi Owner` и `Habibi Staff`,
  раздел с отсутствующим полем пропускается;
- `@selling_price`: чтение действующей цены, запись создаёт `Item Price`;
- `orders.transition` с воркфлоу и без, отправка уведомления заглушкой,
  сорвавшаяся отправка оставляет заказ принятым;
- `chats.pause/resume/send`;
- `apply-preset food` дважды подряд.

Фронт — `yarn build` с проверкой типов. Сценарий проходится руками на
`dev.localhost`: пресет → меню → заказ из Telegram → принять → сообщение
клиенту.

## 9. Что не входит

- Другие вертикали и бронирование по датам (задача 2).
- Создание сайтов и включение разделов из `saas_bridge` (задача 3).
- Брендинг кабинета: логотип, цвета.
- WhatsApp в переписках — экран готов к нему, адаптера нет.
- Правка промпта владельцем.
- Аналитика и отчёты.

## 10. Отклонения реализации

Ниже — расхождения между этим документом и тем, что реально заведено в коде
(проверено сквозной проверкой, задача 16). Правильно то, что в коде;
документ ниже поправлен под него.

- **Методы кастомных экранов — в `habibi_ai.cabinet.*`, а не в
  `habibi_ui.api.v1.*`.** Раздел 4.2 верен для `config/list/get/save/delete`
  generic-разделов (Меню, Клиенты, Заказы как список) — они читают только
  `Cabinet Settings` и целевой DocType, поэтому живут в `habibi_ui`.
  Но «Переписки», «Режим работы», «О компании», «Telegram» и действия
  заказа (`orders.transition`, `orders.notify`) нужны в паре с доменными
  доктайпами `habibi_ai` (`AI Channel Chat`, `Business Profile`,
  `Working Hours`, `AI Order Quote`, `Telegram Account/Chat`) — а
  `habibi_ui` не имеет права импортировать `habibi_ai` (правило зависимостей
  «фронт-платформа не знает про ИИ-модуль»). Поэтому эти методы — прямые
  `@frappe.whitelist()` в `habibi_ai.cabinet.chats`, `habibi_ai.cabinet.orders`,
  `habibi_ai.cabinet.settings`, и фронт вызывает их по полному пути
  `habibi_ai.cabinet.<модуль>.<метод>`. Связь `habibi_ui` → `habibi_ai` в
  обратную сторону — только через хуки `habibi_cabinet_adapters` (поле
  `@selling_price`) и `habibi_cabinet_features` (флаги 4.4), которые
  `habibi_ai` объявляет в своих `hooks.py`, а `habibi_ui` читает по имени, без
  импорта.

- **Флаги возможностей — два поля `Check` на `Habibi AI Settings`
  (`feature_delivery`, `feature_orders`), а не таблица.** Раздел 4.4 говорил
  о «таблице включённых возможностей»; в коде (`habibi_ai/features.py`) это
  просто по одному чек-боксу на возможность. Значение **не сохранённого
  вообще** поля (`None` — сайт мигрировал раньше, чем завели флаги) считается
  «включено»: иначе сайт, где бот уже принимал заказы, потерял бы
  `quote_order`/`create_order` молча после обновления. Пустая строка ("" —
  как приходит из `frappe.db.get_singles_dict` без каста) равносильна `0`.
  Итог: **не заведено или пусто = включено**, `0`/выключен явно = выключено.

- **Бизнес-профиль уходит в движок полем `tenant_context`, а не отдельным
  сообщением.** `habibi_ai.api.tenant_context()` собирает блок профиля (см.
  раздел 5) и передаёт его в `Engine.step(..., tenant_context=...)`
  (`habibi_ai/engine.py`); `habibi_ai_engine` дописывает его в системный
  промпт (`composeSystemPrompt`, `extensions/ai/src/process-message`). Это и
  есть «движок не ниже коммита задачи 1» из чек-листа включения ниже —
  без параметра `tenant_context` в `/process` профиль до бота не доедет.

- **`notify(name, text)` — без параметра `chat`.** По плану уведомление
  клиента после «Принять»/«Отклонить» должно было принимать чат явным
  параметром; в реализации (`habibi_ai.cabinet.orders.notify`) чат берётся
  только из `AI Order Quote` по `sales_order == name` — клиентский `chat`
  был бы дырой в правах (можно было бы написать в любой чужой чат). Если
  заказ уже удалён (черновик бота отклонили удалением), метод требует
  `AI Order Quote` с этим `sales_order` **и** право `delete` на `Sales
  Order` у вызывающего — то есть уведомить после удаления можно только тому,
  кто мог бы удалить заказ сам. Пустой текст отбрасывается до отправки.

- **Живое обновление (раздел 7) — адресно по пользователям, не broadcast.**
  `frappe.publish_realtime` без `room`/`user` уходит всем, кто подключён к
  сайту, включая портальных пользователей. `habibi_ai.cabinet.realtime`
  вместо этого шлёт `publish_realtime(event, payload, user=...)` по одному
  на каждого пользователя с ролью `Habibi Owner`, `Habibi Staff` или `System
  Manager` (без `Administrator`) — в малом бизнесе это одна-три учётки, цикл
  дешевле, чем городить под роли отдельную комнату, которой во Frappe для
  ролей и нет.

- **«Отклонить» черновик без перехода воркфлоу — это удаление, отдельным
  от воркфлоу действием.** Прод-воркфлоу `Habibi Burger Order` (раздел 2) не
  даёт перехода из `New` ни в один статус, кроме `Confirm` → `Confirmed`:
  явного «отклонить черновик» там нет. Раздел 6.1 обещает кнопку
  «Отклонить» на любом черновике бота — поэтому `orders.apply` вида
  `action="reject"` при доктайпе в статусе `New` (`docstatus == 0`) и
  отсутствии подходящего перехода воркфлоу предлагает третий, не воркфлоу-вый
  вид действия: удалить документ (`frappe.delete_doc`, с проверкой права
  `delete`) — то есть «отклонить» черновика от бота технически означает
  «отказаться от него», а не «провести отказ». У проведённого (`docstatus ==
  1`) заказа без воркфлоу действий в кабинете нет вовсе
  (`orders._available` отдаёт пустой список): обещанного разделом 6.1
  `cancel` проведённого без воркфлоу нет — отменить такой заказ можно в
  Desk. Проведённый заказ с воркфлоу отклоняется переходом воркфлоу
  (`reject_action`).

- **Имена действий воркфлоу на проде — `Confirm` (принять) и `Cancel Order`
  (отклонить проведённый).** Раздел 6.1 говорит «имена действий задаёт
  пресет»; пресет `food.json` прибивает их к именам, реально заведённым на
  `erp.habibi-erp.com` (раздел 2) — `{"accept_action": "Confirm",
  "reject_action": "Cancel Order"}`. Без пресета (сайт без воркфлоу или с
  другим воркфлоу) `habibi_ai.cabinet.orders._names()` откатывается на те же
  два имени по умолчанию.

- **Выкатка.** Порядок и оговорки, без которых кабинет встанет не целиком:
  - движок (`habibi_ai_engine`, ветка `feat/tenant-context`) должен быть
    выкачен, иначе бизнес-профиль до бота не доходит: старый движок поле
    `tenant_context` молча игнорирует (ошибки нет, профиля в промпте тоже);
  - перед сменой образа — бэкап сайта;
  - `bench migrate` — до перезапуска воркеров: новые хуки (realtime,
    адаптеры) ссылаются на поля и DocType, которых до миграции нет;
  - пресет выдаёт права через `add_permission`, а тот переводит стандартные
    права затронутых DocType (Item, Sales Order, Account…) в Custom DocPerm
    (`copy_perms`). Дальше для этих DocType на сайте действуют только
    Custom DocPerm — будущие изменения прав в JSON приложений (ERPNext,
    habibi_*) сами туда не доедут, их придётся переносить вручную.
