# Достоверность агента: обязательства и следы инструментов

Состояние на 2026-09-29. Продолжение `2026-09-10-agent-core-design.md`
(принцип «состояние меняет код, а не намерение модели») и
`2026-09-19-orders-and-hours-design.md` (приём заказов). Первый из трёх
подпроектов: 1 — достоверность (этот файл), 2 — память о клиенте, 3 — сжатие
контекста. Подпроекты 2 и 3 строятся поверх этого, каждый получит свою спеку.

## 1. Задача

Бот не должен сообщать о действии, которого не совершал, а если клиент
согласился на действие, оно должно быть совершено.

### Что случилось

28.09 на `erp.habibi-erp.com` бот трижды ответил клиенту «Заказ оформлен:
SAL-ORD-2026-00024/25/26. Статус: draft». В ERP таких заказов нет: последний
существующий — 00023, счётчик серии равен 23. Расчёты AIQ-00010/11/12 созданы,
но `sales_order` у них пуст.

Установлено по логам движка и данным:

- в ход клиентского «да» модель не вызвала `create_order` — в логе за эти ходы
  только `get_menu`, `get_delivery_zones`, `quote_order`;
- номера выдуманы: каждый следующий на единицу больше предыдущего;
- причина в двух дырах. (а) В `chat_messages` пишутся только реплики человека и
  финальные ответы, вызовов инструментов история не содержит, и модель
  копирует из неё шаблон «да → Заказ оформлен: SAL-ORD-… Статус: draft…».
  (б) Правило «заказ создан — только пересказом ответа `create_order`» лежит
  лишь в промпте, кодом ничто его не проверяет.

Промпт уже говорит то, что нужно; повторное усиление промпта той же ошибки не
исключает. Нужна проверка кодом.

### Цели

1. Утверждение бота о действии либо подтверждено результатом инструмента в
   этом ходе, либо не доходит до клиента.
2. Если согласие клиента получено, а действие не совершено — его совершает код,
   а бот пересказывает реальный результат.
3. Модель видит в истории, что реально было сделано, и не копирует ложный
   образец.
4. Новые «обязательства» (другие инструменты) добавляются записью в реестр, без
   правки цикла.

### Не цели

- Чтение заказов и статусов, профиль клиента, предпочтения — подпроект 2.
- Сжатие и резюме истории — подпроект 3. Здесь только закладывается формат
  следа, на котором оно будет строиться.
- Проверка фактов вне инструментов (цены, режим работы в свободном тексте).

## 2. Решение

### 2.1 Реестр обязательств

Новый модуль `habibi_ai/commitments.py`. Как `loop.py` и `engine.py`, не
импортирует `frappe`: это переносимая часть ИИ-модуля.

Обязательство — запись с тремя частями:

| Часть | Для заказа |
|---|---|
| `claims(text)` — что в тексте считается утверждением о действии | номер вида `SAL-ORD-\d{4}-\d+` или фраза «заказ (оформлен\|создан)» (регистр не важен) |
| `confirmed(turn, text)` — чем оно подтверждено | в `turn` есть пара `create_order` с результатом, начинающимся `Заказ <номер> (уже )?создан`, и каждый номер из текста совпадает с номером из результата |
| `fulfil` — инструмент, который довыполняется | `create_order` (без аргументов) |

Подтверждением служит именно начало результата, а не наличие номера: отказ
«Заказ … был удалён оператором» тоже содержит номер, но заказом не является.

Реестр — список `COMMITMENTS`; цикл про заказы ничего не знает.

### 2.2 Поведение цикла

`loop.run` получает параметр `commitments` (по умолчанию пусто — поведение цикла
для существующих вызовов не меняется). Когда модель вернула текст:

1. Для каждого обязательства: если `claims(text)` и не `confirmed(turn, text)` —
   нарушение.
2. Нет нарушений — текст уходит как раньше.
3. Нарушение, довыполнение по этому обязательству в ходе ещё не было:
   - текст модели отбрасывается;
   - цикл вызывает `execute(fulfil, {})` — тот же путь исполнения, что и у
     обычного вызова, с проверкой «инструмент предложен на ходу»;
   - в `turn` добавляется пара `tool_use`/`tool_result` с синтетическим id
     `guard-<n>` и без `raw`; формат уже поддержан обоими провайдерами;
   - следующий виток пересказывает клиенту настоящий результат. Виток
     довыполнения тратит общий лимит `max_loop`.
4. Нарушение после довыполнения (модель снова врёт): клиенту уходит не текст
   модели, а «пересказ по результату» — предложение, собранное кодом из
   результата последнего инструмента (для заказа — его первая строка вместе с
   номером). Ложь наружу не выходит ни при каком исходе.

Условия самого `create_order` остаются прежними и защищают от лишних заказов:
последний расчёт чата, не просрочен, сообщение клиента пришло после расчёта и
расчёт был зачитан клиенту. Если не выполняется любое — инструмент возвращает
отказ, модель честно передаёт его. Повтор идемпотентен: тот же расчёт даёт тот
же заказ.

Довыполнение — это компенсирующее действие только для инструментов, которые
безопасно вызвать без аргументов повторно. Это свойство обязательства, оно
фиксируется в реестре явно; вписать туда инструмент с аргументами нельзя.

### 2.3 Следы инструментов в истории

Движок на финальном шаге хода уже получает `turn`. Сейчас он сохраняет только
`content`. Меняется так:

- в коллекцию `chat_messages` добавляется поле `tool_trace` (json, может быть
  пустым) — список `{name, input, result}`, где `result` обрезан до 200
  символов. Записывается вместе с финальным ответом ассистента;
- `getChatMessages` возвращает его вместе с `role`/`content`;
- при сборке сообщений для провайдера (`buildOpenAIMessages`,
  `buildAnthropicMessages`) к реплике ассистента добавляется строка
  `[инструменты: create_order → Заказ SAL-ORD-2026-00023 создан]` — только для
  модели. Клиенту и консоли уходит прежний `content`; сама колонка нигде не
  показывается.
- служебные инструменты чтения (`get_menu` и подобные) в след не пишутся, чтобы
  не раздувать историю: пишутся только инструменты, меняющие данные. Признак
  «пишущий» — поле в определении инструмента (`records: true`), по умолчанию
  ложь.

Схема Directus обновляется через `schema/snapshot.yaml` и применяется на проде
при выкатке движка.

Побочный эффект, важный для подпроекта 3: у резюме появляется структурный
источник фактов («создан заказ N»), а не только пересказ текста.

### 2.4 Что не меняется

- Протокол шага движка, контракт `turn`, формат инструментов.
- Права и изоляция тенантов: довыполнение идёт тем же `execute` под правами
  тенанта, движок учётных данных не получает.
- Промпты сценариев. Правило про `create_order` остаётся: оно снижает частоту
  нарушений, а код гарантирует результат.

## 3. Обработка ошибок и наблюдаемость

- Каждое срабатывание стража пишется в трассировку (`debug`) шагом
  `commitment_violation` с именем обязательства и фрагментом текста.
- Без `debug` — в `frappe.logger("habibi_ai")` уровнем warning: страж не должен
  срабатывать часто, а если срабатывает, это сигнал качества модели или
  промпта.
- Отказ довыполняемого инструмента не ошибка стража: его текст — обычный
  результат инструмента.
- Сбой самого стража (исключение в `claims`/`confirmed`) не блокирует ответ:
  ход завершается как без стража, ошибка пишется в Error Log. Страж добавляет
  надёжности и не должен сам её отнимать.

## 4. Тесты

`loop`:
- утверждение подтверждено — текст уходит без изменений;
- утверждение без вызова — довыполнение, ответ по реальному результату;
- довыполнение вернуло отказ — модель передаёт отказ, номера в тексте нет;
- повторная ложь после довыполнения — клиенту уходит пересказ по результату;
- выдуманный номер при реальном вызове `create_order` с другим номером;
- отказ «был удалён» с номером в тексте не считается подтверждением;
- инструмент не предложен на ходу — довыполнения нет, ход идёт как обычно;
- лимит `max_loop` учитывает виток довыполнения;
- сбой стража не роняет ход.

`commitments`: сопоставление номеров и фраз, регистр, несколько номеров в тексте.

Движок: сборка истории с `tool_trace` для OpenAI и Anthropic; пустой след;
обрезка результата; служебные инструменты не пишутся.

Регрессия на инциденте: сценарий «расчёт → да» с моделью, не вызывающей
`create_order`, заканчивается созданным заказом, а не выдуманным номером.

## 5. Выкатка и проверка

1. Движок: тег `habibi_ai_engine`, образ в CI, `AI_ENGINE_TAG` в
   `~/habibi_docker/.env`, `docker compose up -d ai-engine`; схема с
   `tool_trace` применяется вместе с движком.
2. Приложение: тег `habibi_docker`, деплой по обычному пути (бэкап, миграция).
   Порядок важен: сначала движок (поле и сборка истории обратно совместимы,
   старый `habibi_ai` след просто не присылает), затем приложение.
3. Живая проверка на `erp.habibi-erp.com` в консоли отладки и в Telegram-чате
   тестового клиента: расчёт → «да» → в ERP появился заказ с тем номером,
   который назвал бот; счётчик серии совпал.

## 6. Решения и что осталось открытым

Принято:
- довыполнение, а не честный отказ: согласие клиента получено, действие должно
  совершиться (решение владельца, 2026-09-29);
- страж живёт в `habibi_ai`, а не в движке: только там есть тенант, права и
  результаты инструментов;
- след пишется в колонку, а не в текст `content`: чтобы не загрязнять то, что
  видят люди и что читают кабинет и консоль.

Открыто (решается в плане, на дизайн не влияет):
- точная формулировка «пересказа по результату» для не-заказных обязательств;
- нужно ли отдельное уведомление оператору о срабатывании стража — сейчас
  только журнал.
