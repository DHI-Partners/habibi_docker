# Ядро агента: инструменты вместо роутера намерений

Дата: 2026-09-10
Статус: черновик, на согласовании

Заменяет архитектурное ядро, описанное в
[2026-08-29-habibi-ai-design.md](2026-08-29-habibi-ai-design.md). Изоляция
тенантов, разделение на движок и модуль, консоль отладки из
[2026-09-07](2026-09-07-habibi-ai-frontend-design.md) сохраняются без
изменений.

## 1. Задача

Нужен **универсальный сотрудник**: одна и та же машина, которой инструкцией и
набором инструментов задаётся профессия. Сотрудник кафе принимает заказы, знает
актуальное меню, фиксирует жалобы. Учитель принимает домашние задания и
объясняет темы. Ассистент разбирает переписку.

Нынешнее ядро этого не даёт и, кроме того, ненадёжно.

### 1.1 Почему нынешнее ядро ненадёжно

**Классификатор намерений не видит разговора.** `callLLM(systemPrompt,
userMessage)` передаёт модели ровно одну реплику. Намерение «продолжим» или
«да» определить по ней невозможно — не с чем соотнести. Отсюда сбои возврата к
предыдущей теме, которые выглядят случайными.

**Вероятностный сигнал управляет точным состоянием.** Отвечающая модель должна
не забыть тег `[DONE]`, по которому детерминированно выталкивается
`scenario_stack`. Забыла — состояние разъехалось с разговором, молча.

**Факты живут прозой в промпте.** Режим работы и минимальный заказ записаны
абзацем, и бот их **пересказывает**, а не читает. Проверить пересказ нечем.

**История обрезается.** `max_history_messages` отрезает начало. Для сборки
заказа это смертельно: состав уезжает из окна, и бот забывает, что заказали.

Общий корень: **состояние диалога хранится снаружи модели, а управляется
изнутри неё.**

## 2. Решение

Один агент. Одна инструкция на роль. Инструменты. Цикл вместо конвейера.

Модель видит переписку целиком и сама решает, что спросить и что вызвать.
Классификатор намерений, стек сценариев и возврат к предыдущему **удаляются
целиком** — возврат к теме получается сам собой, потому что темы никогда не
покидали.

### 2.1 Цикл обработки

```
habibi_ai:  переписка + описания инструментов, которые он готов исполнить
    ↓
движок:     подставляет роль и инструкции, зовёт модель
    ↓
модель возвращает одно из двух:
    • текст             → сохранить, отдать пользователю, конец
    • вызов инструмента → habibi_ai исполняет, добавляет результат, повторяет
```

Число витков ограничено (по умолчанию 8, поле бота). Исчерпание лимита —
ошибка, а не молчаливая остановка: цикл без выхода означает, что модель не
может решить задачу имеющимися инструментами, и человек должен об этом узнать.

### 2.2 Цикл ведёт habibi_ai, а не движок

Движок разговаривает с моделью, но не с ERP. Вёл бы цикл он — ему понадобились
бы учётные данные каждого тенанта: одна точка, компрометация которой открывает
всех. Тот же довод, по которому в спеке 2026-08-29 браузер не ходит в Directus.

| | Движок Directus | `habibi_ai` (Frappe) |
| --- | --- | --- |
| Решает | что сказать, какой инструмент нужен | какие инструменты есть, как их выполнить, кому можно |
| Знает про | боты, промпты, сценарии, модель | тенанта, права, ERPNext |
| Не знает про | ERP, тенантов, права | промпты, выбор модели |

Движок остаётся мозгом без рук.

## 3. Контракт эндпоинта

`POST /ai-process-message` меняет смысл: из «дай ответ» в **«дай следующий
шаг»**. Он вызывается несколько раз за один ход пользователя.

### Запрос

```json
{
  "chat_id": 18,
  "bot_id": 1,
  "user_message": "две шаурмы",
  "turn": [
    {"type": "tool_use",    "id": "t1", "name": "get_menu", "input": {}},
    {"type": "tool_result", "id": "t1", "content": "[{\"item\":\"шаурма\",\"price\":350}]"}
  ],
  "tools": [
    {
      "name": "get_menu",
      "description": "Актуальное меню заведения с ценами",
      "input_schema": {"type": "object", "properties": {}}
    }
  ],
  "debug": true
}
```

* `user_message` — новая реплика. Передаётся на каждом шаге хода, движок
  сохраняет её в `chat_messages` **только когда `turn` пуст**, то есть один
  раз за ход.
* `turn` — что уже произошло **внутри этого хода**. Пустой на первом шаге.
* `tools` — описания, которые `habibi_ai` готов исполнить **для этого тенанта
  и этого бота**. Движок их не хранит и не проверяет: он передаёт их модели как
  есть. Знание о том, какие инструменты существуют и кому разрешены, живёт на
  стороне прав.
* `debug` — как сейчас: ставит прокси по роли, браузер повлиять не может.

### Ответ

```json
{"type": "text", "content": "Две шаурмы, 700 рублей. Оформляем?", "debug": [...]}
```

```json
{"type": "tool_use", "id": "t2", "name": "update_draft",
 "input": {"items": [{"item": "шаурма", "qty": 2}]}, "debug": [...]}
```

Ответ ассистента сохраняется в `chat_messages` только при `type: "text"` —
то есть один раз за ход.

### 3.1 Вызовы инструментов не попадают в историю чата

Они живут внутри хода и уходят в трассировку, а не в `chat_messages`.

Причина: переписка — это то, что видели люди. Смешав туда служебные вызовы, мы
раздуем контекст и покажем пользователю мусор. Последствие принимается
осознанно: на следующем ходу модель не помнит, что вызывала `get_menu`, и при
необходимости вызовет снова. Это дёшево и всегда даёт свежие данные.

Долгоживущее состояние — черновик заказа — хранится отдельно (раздел 5) и
переживает и ход, и сжатие истории.

## 4. Конфигурация

**`ai_bots`** — роль сотрудника: `global_system_prompt`, модель, лимит витков.
Меняешь запись — меняешь профессию. Это и есть «универсальность».

**`chatbot_scenarios`** — переосмысляются из состояний в **наборы
возможностей**:

| Поле | Смысл |
| --- | --- |
| `scenario_key` | имя набора, для человека |
| `initial_prompt` | фрагмент инструкции для этого рода задач |
| `tools` | **новое поле**: имена инструментов, разрешённых набором |

`tools` в схеме нет — его надо завести, nullable. База общая с работающим
ботом: старое ядро поля не читает, новое на пустом значении даёт набор без
инструментов и работает как обычный собеседник.

**Имя инструмента, которого нет в реестре `habibi_ai`, игнорируется — с записью
в трассировку.** Не ошибка: конфигурацию правят в админке без ревью, опечатка
неизбежна, и ронять из-за неё весь диалог нельзя. Но и молчать нельзя, иначе
человек будет искать, почему бот «не умеет», а причина в лишней букве.

Все включённые наборы бота **сливаются в одну инструкцию**, их инструменты — в
один список. Никто не выбирает набор в рантайме: модель видит всё сразу.

Поэтому `current_scenario` удаляется. Сценарий перестаёт быть состоянием и
становится способом организовать конфигурацию — чтобы человек правил кафе и
жалобы раздельно, а не одним полем на десять абзацев.

**Инструменты объявляются кодом.** В `habibi_ai` — питон-функция с описанием и
схемой аргументов; в Directus сценарий выбирает имена из доступных. Права и
валидация остаются в коде, под тестами, а не в формочках.

Расширение набора инструментов — правка кода. Это осознанно: инструмент,
заведённый в админке, означал бы произвольный REST-вызов под правами тенанта,
описанный человеком без ревью.

## 5. Состояние задачи

Черновик собираемой задачи — в `customer_chats.metadata`, ключ `draft`.

**Модель ведёт его полным состоянием, а не приращениями:**

```
«и лагман»        → update_draft(items=[шаурма×2, лагман×1])   весь состав
«не две, а три»   → update_draft(items=[шаурма×3, лагман×1])   опять весь
«убери лагман»    → update_draft(items=[шаурма×3])
```

При приращениях модель обязана помнить, что уже отправила, и считать разницу —
именно там она и уплывает. При полном состоянии помнить нечего: она смотрит на
переписку и заново называет результат. Мы валидируем целое.

Удаление позиции при этом не отдельная операция, а состояние без неё.

### 5.1 Жизненный цикл: код по факту, а не модель по намерению

| Событие | Кто выполняет |
| --- | --- |
| собрать, исправить, убрать | модель, вызовом `update_draft` |
| подтвердить | модель, после явного согласия клиента |
| создать заказ | код, с проверкой всего состава |
| **очистить черновик** | **код, по факту создания** |
| отменить по просьбе | модель, вызовом `clear_draft` |

Очистку делает код. Доверить её модели — повторить ошибку `[DONE]`: забыла
вызвать, и следующий заказ начинается с чужими позициями.

**Правило, общее для всей архитектуры: всё, от чего зависит следующий шаг,
меняет код по факту, а не модель по намерению.**

## 6. Контекст

Полная переписка, пока помещается. Дальше — **сжатие старого в резюме**, не
отрезание.

Порог считается по токенам, а не по числу сообщений: пятнадцать реплик о меню и
пятнадцать с длинными объяснениями — разный объём. `max_history_messages`
удаляется: обрезание и есть механизм забывания, от которого мы уходим.

Само сжатие — **вне объёма этой спеки** (раздел 10), и это оставляет известную
дыру: без обрезания и без сжатия достаточно длинный чат однажды перестанет
помещаться в окно модели.

Дыра принимается осознанно и с условием: **переполнение должно давать явную
ошибку, а не молча терять начало разговора.** Тихая потеря — это ровно то
поведение, от которого мы уходим; громкий отказ показывает, что пора делать
пункт 2. До тех пор ограничение снимается началом нового чата.

## 7. Галлюцинации

Новая архитектура убирает один класс и добавляет другой, более опасный.

**Уходит пересказ фактов.** Бот не помнит меню, а спрашивает его.

**Приходят выдуманные вызовы:** несуществующая позиция, неверное количество,
и худшее — «Заказ оформлен!», когда инструмент упал. Галлюцинация перестаёт
быть неверным текстом и становится неверным **действием**.

Защита, по убыванию пользы:

1. **Аргументы проверяются по настоящим данным на сервере.** `create_order`
   сверяет каждую позицию с фактическим меню. Сверху — валидация ERPNext, так
   как инструменты исполняются под правами тенанта.
2. **Отказ возвращается модели текстом**, чтобы она исправилась сама:
   `"пицца" нет в меню. Доступно: шаурма, лагман`.
3. **Уровень доверия на каждый инструмент.** Чтение свободно, жалоба
   фиксируется сразу, заказ требует подтверждения.
4. **Утверждать о результате только по ответу инструмента.** «Оформлен» — если
   вернулся номер.
5. **Схема аргументов** отсекает бессмысленное до кода.
6. **Трассировка как аудит** — галлюцинацию видно, а не подозреваешь.

## 8. Отладка

Консоль из спеки 2026-09-07 работает без переделки. В трассировку добавляются
шаги цикла:

| Шаг | Содержимое |
| --- | --- |
| `tools` | какие инструменты предложены модели на этом шаге |
| `tool_use` | что вызвано, с какими аргументами |
| `tool_result` | что вернулось, включая отказ |
| `loop` | номер витка и лимит |

Черновик виден в панели состояния на каждом ходу: расхождение между сказанным
и записанным ловится глазом, а не по жалобе.

## 9. Что удаляется

| Что | Почему |
| --- | --- |
| `intent_router` и его промпт | классифицировал без контекста |
| `scenario-stack.ts` целиком | обслуживал возврат, которого больше нет |
| `RETURN_TO_PREVIOUS` | худший случай классификации без контекста |
| `[DONE]` и `processAutoReturn` | вероятностный сигнал на детерминированном состоянии |
| `current_scenario`, `scenario_stack`, `max_stack` | состояние переехало в переписку |
| `max_history_messages` | заменяется сжатием |
| `person_key`, `flow_id` | проверено: не используются нигде в коде |

Вместе с `scenario-stack.ts` уходят девять тестов, закреплявших его ветви. Это
не потеря покрытия: они описывали механизм, которого не станет.

**Поля схемы удаляются из кода, но не из базы.** База общая с работающим ботом,
и удаление колонок — отдельная операция после того, как новое ядро отработает.

## 10. Что в эту спеку не входит

Разрезание на самостоятельные части:

1. **Ядро агента** — эта спека. Цикл, контракт, один инструмент `get_menu` для
   проверки.
2. **Сжатие контекста** — резюмирование старого вместо обрезания.
3. **Инструменты кафе** — черновик, подтверждение, заказ, жалоба.
4. **Проверочные диалоги** — набор разговоров с ожидаемыми вызовами, прогон при
   смене модели, промпта или инструмента.
5. **Учитель и ассистент** — новые конфигурации. Кода требовать не должны; если
   потребуют, значит пункт 1 сделан неверно.

Первый пункт самостоятелен: после него бот умеет спрашивать данные, и это
проверяется живьём одним диалогом про меню.

## 11. Грабли

**Не давать модели управлять детерминированным состоянием.** Ошибка `[DONE]`
воспроизводима в новой архитектуре — например, поручив модели очищать черновик.
Всё, от чего зависит следующий шаг, меняет код.

**Не доверять аргументам.** Модель называет позиции текстом, и текст бывает
правдоподобным, но несуществующим. Сверять с данными, а не с ожиданиями.

**Не складывать вызовы инструментов в историю чата.** Раздувает контекст и
показывает пользователю служебное.

**Не считать, что «инструментов нет» — это поломка.** Бот без инструментов —
законная конфигурация: так работает собеседник, который только отвечает. Пустой
набор не должен приводить к ошибке ни в движке, ни в прокси.

**Не переносить сценарии как состояние.** Соблазн оставить `current_scenario`
«на всякий случай» вернёт ту же рассинхронизацию: поле, которое кто-то будет
писать, а кто-то читать, не совпадая с разговором.
